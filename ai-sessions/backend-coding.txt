  The tests replace the global fetch with a mock (vi.stubGlobal), so they never

  Why each test exists

  1. Maps Open-Meteo results to domain Locations
  This is the provider's main job: turning Open-Meteo's response into the domain
  Location type. It checks the three parts of that mapping that could break
  silently:
  - id becomes a string (Open-Meteo sends a number, and GraphQL ID is a string).
  - admin1 is renamed to region.
  - Extra fields like timezone are dropped.

  It uses toEqual on the whole object, so a missing field, a renamed field or a
  leftover field all fail the test.

  2. Leaves country and region undefined when Open-Meteo omits them
  Open-Meteo doesn't always send country or admin1, for example for small places
  or places in disputed territory. This makes sure a missing field comes
  through as undefined and doesn't crash. That matters because the GraphQL
  schema declares those fields as optional (String, not String!).

  3. Returns [] when Open-Meteo has no matches
  This is the behaviour we saw in the live test with "L". On no matches, the API
  leaves out results entirely; it doesn't send an empty array. Without the ??
  [], the code would call .map on undefined and throw. The mock response copies
  the real one ({ generationtime_ms } only) so the test matches what the API
  actually returns.

  4. Returns [] for blank input without calling Open-Meteo (runs for "" and "
  ")
  This is your decision a1 in DECISIONS.md. The test checks two things:
  - The result is [].
  - fetch is never called.

  The second check is the important one. Without it, deleting the guard would
  still pass, because the API would return no results anyway. Running it with
  whitespace-only input also confirms the input is trimmed before the blank
  check.

  5. Sends a trimmed name with the expected query params
  This pins down the exact request:
  - the endpoint URL
  - name trimmed
  - count=3 by default (your decision a2)
  - language=en
  - format=json

  Comparing all the parameters at once also catches any extra parameter added by
  accident. Trimming matters for a real reason: a user typing "London " would
  otherwise send a trailing space.

  6. Passes a custom count through
  The count argument is part of the method's signature. This checks that a
  caller-supplied value actually reaches the URL and isn't overridden by the
  default.

  7. Sends an abort signal so slow requests time out
  This covers your 5-second timeout decision. Testing the actual 5 seconds would
  mean fake timers or a slow test, so it only checks that a signal is passed to
  fetch. If someone removes the timeout, this test fails. It does not check the
  exact duration; I chose that trade-off on purpose.

  8. Throws when Open-Meteo responds with an error status
  fetch doesn't throw on HTTP 4xx or 5xx responses; it only throws on network
  errors. Without the response.ok check, an error page would be parsed as if it
  were data. This test makes sure an upstream 500 becomes a clear error with the
  status in the message, which GraphQL Yoga then reports as an error. It does
  not quietly return [] and look like "no results".

  9. Propagates network failures
  This covers DNS failures, a dropped connection, or the timeout itself firing.
  It checks that the provider doesn't swallow the error and return []. The user
  should see that something went wrong, not "no cities found".

⏺ You're right, and my explanation of test 8 was wrong. Yoga masks errors by
  default: any error that isn't a GraphQLError reaches the client as "Unexpected
  error.", so the status code never gets there. In development mode, Yoga also
  adds the original error under extensions, which is why it can seem to come
  through when you test locally. The provider's message still matters for server
  logs, so test 8 is still worth keeping. It just isn't something the client
  sees.

  For the UI, a masked error is hard to handle well, because the UI can't tell
  "Open-Meteo is down" apart from a bug in your own code. If you want to
  separate them, catch the error in the resolver and rethrow it as a
  GraphQLError with a code:

  searchLocations: async (_parent, args: { name: string }) => {
    try {
      return await geocoding.search(args.name);
    } catch (error) {
      throw new GraphQLError("Location search is unavailable", {
        originalError: error as Error,
        extensions: { code: "UPSTREAM_UNAVAILABLE" },
      });
    }
  },

  That keeps the provider independent of GraphQL, which matches your
  DECISIONS.md note. Yoga passes GraphQLErrors through without masking. The UI
  can then check extensions.code and show something like "Search is temporarily
  unavailable, try again".

  If you'd rather keep the masked error and show a generic message, that works
  too. It's just less specific.

  Choices you didn't ask for

     exactly.
  2. DayScore and ScoreFactor are in domain/types.ts, next to DailyWeather.
  3. The missing-data reason is in a field called missingData, and it names the
     fields, e.g. "Missing forecast data: wind gusts, weather code".
  4. The missing-data check runs before the gates. You might want to change this
     one. A day with gusts of 102 km/h but no precipitation value returns null,

  Things to look at

  1. Chamonix 8 Jan is now gated. Its base is exactly 10 cm. The session used "<
     10" and scored it 39; your gate is "≤ 10" inclusive, so it scores 0 with
     "Not enough snow: 10 cm base". The test checks for the gate. If you want
     the session's behaviour, change the gate to "< 10".
  2. Open-Meteo doesn't produce 23- or 25-hour days. It returns 24 hours on DST
     switch days, using one fixed UTC offset per response. For example,
     2026-03-29T02:00 appears even though that time doesn't exist in France.
     - Grouping by date still works, and stays correct if the API changes.
     - The DST test uses a made-up series: a 23-hour day and a 25-hour day, set
       up so that grouping in blocks of 24 would fail.
     - Side effect: after a DST change in the week, later days' hours are
       shifted by an hour. For a daily minimum that hardly matters.
