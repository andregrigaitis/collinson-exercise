⏺ No real worries for this app as it stands. Yoga's default CORS is very open,
  but there's nothing behind it that an open policy exposes.

  What the default does: I read Yoga's CORS plugin (it lives in
  @whatwg-node/server/esm/plugins/useCors.js). With no options set, it copies
  whatever Origin the browser sends back as Access-Control-Allow-Origin, and it
  also sends Access-Control-Allow-Credentials: true. So any website can call the
  API from a visitor's browser, cookies included.

  Why that's fine here:
  - There's no login, cookies or per-user data, so another site sending your
    cookies along gains nothing.
  - There are no mutations. A request from another site can't change anything,
    it can only read public weather data.

  What CORS doesn't protect anyway: CORS only limits browsers. Anyone can call
  the API with curl, and each call goes on to Open-Meteo, so the real exposure
  is people using your server as a free proxy and burning your Open-Meteo quota.
  The fix for that is rate limiting or caching, not CORS. That's out of scope
  for the exercise, but it could be a line in DECISIONS.md.

  If you want to tighten it:
  - Restrict the origin: createYoga({ schema, cors: { origin:
    'http://localhost:5173' } }) in index.ts (server/src/index.ts). In a real
    deploy you'd read it from an env var. Leaving out credentials stops it
    sending the credentials header.
  - Use a Vite dev proxy instead (my pick): proxy /graphql to localhost:4000 in
    vite.config.ts and change the default API_URL in graphql.ts
    (web/src/api/graphql.ts) to /graphql. The browser then sees one origin, CORS
    stops being involved, and the setup matches a typical deploy where both sit
    behind the same host. You can still turn off Yoga's CORS on top of that.

  Either change is a few lines if you want it now; otherwise it's a short note
  in DECISIONS.md.
